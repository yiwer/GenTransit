## 1. 现状实测（2026-10-30，提交 `1001649`）

**环境：** 设计规模的临时库（站点 2 万铺成约 33×42 公里的城市网格，线路 3000、走向 6000 且全部带轨迹（每条约 290 点），途经 18 万，站架 5 万，站牌 10 万，编排 16 万；另造一个 128 个走向经过的枢纽站）。生产构建的服务端在本机托管前端，浏览器与服务端同机，**没有限速**，所以下面的耗时只反映服务端和浏览器本身，网络慢时的差距主要来自传输量。

**结论：服务端和地图都不慢，慢在传输量。** 列表、详情、编辑器接口 8–40 ms；线路列表地图 100 条线路（200 个走向、约 4.7 万点）拖动缩放，最长一帧 14 ms。

### 1.1 传输量

| 项 | 现状 | 原因 |
|---|---|---|
| 压缩 | 无。JSON、JS、CSS 全部原样传输 | 服务端没有压缩中间件，部署也没有反向代理 |
| 首次访问静态资源 | 约 3.7 MB：JS 1.13 MB（单个包）、CSS 0.82 MB、字体分片 57 个约 1.7 MB | JS 没有按页面分包；CSS 的 92%（755 KB）是 634 条 `@font-face`；字体保持现状（Q78） |
| 静态资源缓存 | `max-age` 7 天 | 带内容哈希的文件可以缓存一年 |
| 线路列表 | 20 条 295 KB，100 条 1.46 MB | 每个走向带完整轨迹（每条约 6.5 KB） |
| 站点列表、站牌集列表 | 打开页面就下载 `/api/lines?size=100`，1.46 MB | "经过线路"筛选的选择器用了完整的线路列表接口，而且不等打开就加载 |
| 全局搜索的线路结果 | 5 条约 75 KB | 同样用完整的线路列表接口 |
| 站点详情（枢纽站，128 个走向） | 109 KB | 每个经过走向带站点连线，合理，压缩后约 20 KB |

### 1.2 服务端耗时（热缓存，本机）

| 接口 | 耗时 | 说明 |
|---|---|---|
| `/api/sign-sets/summary` | 251 ms | 全部站牌集的编排计数（`SignSetStatusService.countsCte`） |
| `/api/sign-sets?pending=1&sort=-pending&size=5` | 305 ms | 同上，再按待处理排序 |
| `/api/sign-sets/queue?from=home` | 264 ms | 同上 |
| `/api/data-checks` | 244 ms | 线路检查项有版本缓存，但每次都重算 `status.summary` |
| 其余接口 | 4–67 ms | 线路列表 100 条 62 ms 主要是序列化轨迹 |

工作台一次打开就把同一份编排计数算 4 遍（并行，本机约 340 ms 全部返回）；部署建议的 2 核服务器上它们会互相抢 CPU。

### 1.3 其他

- **请求串行：** 站点详情先取 `/api/stops/:id`，返回后才取 `/api/stops/:id/sign-set`，多一个往返。
- **缺陷：** "经过线路"选择器用前 100 条线路去找已选线路的名称，3000 条线路时选中第 100 条以后的线路，筛选条上显示不出名称。
- **JS 构成：** react-dom 206 KB、zod 92 KB、react-router 91 KB、各页面代码约 350 KB、@tanstack 82 KB、@dnd-kit 45 KB（只有站牌集编辑器用）。

## 3. 后端

### 3.1 压缩（P1）

- 在 `configureApp`（`apps/server/src/app.setup.ts`）里加 `compression` 中间件，放在静态资源与 API 之前，对接口 JSON 与前端静态资源同样生效。
- gzip，阈值 1 KB；图片、视频、woff2 等已压缩的类型跳过（中间件默认按 Content-Type 判断）。**默认，可改**
- 导出（CSV、xlsx）是下载流，`xlsx` 本身已压缩，CSV 压缩后照常下载；确认导入进度轮询、上传接口不受影响。
- 部署手册第 4 节补一句：前面有 Nginx 时可以由 Nginx 压缩，应用里的压缩照常工作，两者不冲突（Nginx 看到已压缩的响应不会再压）。

### 3.2 静态资源缓存（P2）

- `/assets/` 下带内容哈希的文件：`Cache-Control: public, max-age=31536000, immutable`。
- 其他静态文件（如 `favicon.svg`）：`max-age=86400`。`index.html` 保持 `no-cache`。**默认，可改**

### 3.3 线路列表不带轨迹（P3，Q79）

- `LineRouteSummary` 去掉 `track`；`LineService` 的列表查询不再选 `track` 等字段（`LIST_INCLUDE`），`toListItem` 不再计算轨迹。
- 线路详情 `RouteDetail.track` 不变；只读 API 不变。
- 列表接口的其他调用方（全局搜索、加入线路对话框）随之变轻，不用另改。

### 3.4 线路选项接口（P4）

- 新增 `GET /api/lines/options?q=&ids=&size=`：只返回 `{ id, name, status }`，按线路列表的自动排序；`q` 匹配线路名与管理编号，`ids` 按 id 取（用于显示已选线路的名称），`size` 默认 20、最多 100。**默认，可改**
- 站点列表与站牌集列表的"经过线路"选择器、加入线路对话框（`JoinLinesDialog`）改用它。

### 3.5 编排计数缓存（P5）

- 在 `SignSetStatusService` 里加一份全部站牌集的计数快照：`Map<signSetId, { waiting, placed, hidden, invalid }>`，按**数据版本**缓存，版本变了才重算。
- 版本：`Line`、`Route`、`RouteStop`、`SignSet`、`Shelf`、`Board`、`Slot`、`Schedule`、`Stop` 的行数，加上其中有 `updatedAt` 的表的最大 `updatedAt`（写法同 `DataCheckService.lineSets`）。编排（`Schedule`）没有 `updatedAt`，但编辑器保存时站牌集的 `updatedAt` 会变，删除与新增由行数反映。实现时核对每条写入路径（线路保存、停运与恢复、站点删除与替换、编辑器保存、导入、M5 的成组修改）都会改变版本，并为每条加一个"改完立即反映"的测试。
- 并发去重：版本相同的并发请求共用同一次计算（同一个 Promise）。
- 用到快照的地方：
  - `summary()`（工作台汇总、站牌集列表页头）。
  - 数据体检的 `pendingSets`。
  - 逐站编排队列（`queue`，工作台与列表来源）。
  - 站牌集列表的"只看待处理"与"按待处理排序"：先用 SQL 按其他筛选条件取出 id（不算计数），再用快照过滤、排序、分页，最后按本页 id 读取行。默认排序（站名）且不筛待处理时照旧只算本页计数。
- 编辑器读取、保存与线路影响分析仍按需实时计算，不读快照（它们只算少数几个站牌集，本来就快，而且必须是最新值）。

### 3.6 其他

- 站点详情接口不变；P7 只改前端的请求时机。

## 4. 前端

### 4.1 线路列表地图（P3）

- 地图一律按站点连线（`points: r.path`，`road: false`），上下行线型、线路颜色不变（F-COM-15）。
- 图例的虚线一行写"虚线：按站点连线"（同站点详情，不再说"未算轨迹"）；选中线路浮出的卡片里各走向的线型示意一律画虚线。
- `LineRouteSummary` 去掉 `track` 后，类型检查会指出所有用到的地方。

### 4.2 线路选择器（P4）

- `LineFilter`（`apps/web/src/features/stops/StopListPage.tsx`，站牌集列表复用）：
  - 候选列表只在弹出层打开时加载（`enabled: open`），输入时按 `q` 防抖查询。
  - 已选线路的名称用 `ids` 查询。
- `JoinLinesDialog` 的线路搜索改用选项接口。

### 4.3 按页面分包（P6）

- 路由（`apps/web/src/app/router.tsx`）的各页面改用 React Router 的 `lazy`；外壳（侧栏、全局搜索、登录页）保留在首包。
- 切换页面时如果代码还没下载完，内容区显示与现有加载态一致的小动画（`OrbitLoader`），外壳不闪。
- 首屏渲染后，在浏览器空闲时预取站点、线路、站牌集三组页面的代码，之后切换不用等。**默认，可改**
- 地图（高德加载器与覆盖层）、站牌集编辑器（@dnd-kit）、导入、设置、基础数据各成一包。

### 4.4 并行请求（P7）

- 站点详情：进入页面时同时请求站点详情与站牌集（`prefetchQuery`），不等详情返回。
- 其他页面按同一原则检查一遍：请求的参数在 URL 里就有的，不要等上一个请求返回再发。

## 6. 测量与前后对比（P8）

- **数据：** 把本次排查用的造数脚本整理进仓库：`apps/server/scripts/perf-seed.ts`，不进测试，手动运行。**默认，可改**。第 1 节的数据就是这样造的：
  - 站点 125×160 网格，间距 0.0028°×0.0024°（约 270 米），中心 (120.2, 30.25)，各带 ±30% 抖动。
  - 每条线路的上行在网格上随机游走 30 个不重复的格子（七成概率沿原方向），下行是上行倒序。
  - 轨迹在相邻站之间插 10 个点，加微小扰动；`trackKey` 用共享包的 `trackKeyOf`，保证不过期。
  - 站牌集、站架、站牌、编排沿用 `test/design-scale.ts` 的 SQL。
  - 再挑 60 条线路，把上下行第 15 站都换成同一个站，造出 128 个走向经过的枢纽站。
  - 随机数用 mulberry32 这类 32 位整数算法。不能用 `seed * 1103515245` 这种浮点写法，超过 2^53 会丢精度，序列很快循环，第一次造数就因此只有 2000 个站点有线路经过。
- **测量：** `apps/web/perf/measure.ts`，用 Playwright 的 Chromium 打开生产构建：
  - 用 CDP 模拟网络：下行 10 Mbps、上行 5 Mbps、往返 40 ms（Q77）。
  - 每页量两次：清缓存后的首次访问，以及有缓存的再次访问。
  - 每次记录传输字节数（压缩后）、数据就绪时间（页面的接口全部返回）、最大内容绘制时间。
  - 再对第 1.2 节的接口各请求 4 次，记录服务端耗时。
  - 输出一张 Markdown 表。**默认，可改**
- **页面：** 工作台、站点列表（20、100 条）、站点详情（普通站、枢纽站）、线路列表（20、100 条）、线路详情、站牌集列表、站牌集编辑器（枢纽站）、全局搜索一次。

## 10. 完成记录（2026-10-30）

### 10.1 做了什么

| 编号 | 实现 |
|---|---|
| P1 | `configureApp` 最前面加 `compression`（1.8.2，gzip，阈值 1 KB），接口 JSON、JS、CSS、index.html 都压缩；woff2、图片、视频、xlsx 按 Content-Type 跳过。部署手册第 4 节补了与 Nginx 压缩的关系 |
| P2 | 静态资源：`/assets/` 下 `public, max-age=31536000, immutable`，其他文件 `public, max-age=86400`，`index.html` 与页面路由 `no-cache` |
| P3 | `LineRouteSummary` 去掉 `track`，线路列表查询不再取轨迹字段；列表地图按站点连线，图例"虚线：按站点连线"，卡片里的线型示意画虚线。线路详情与只读 API 照旧带轨迹 |
| P4 | `GET /api/lines/options?q=&ids=&size=`，返回 `{ items: { id, name, status }[], total }`，按线路自动排序；`q` 匹配线路名与管理编号；`ids` 按 ID 取，给了就不看 `q` 与 `size`；`size` 默认 20、最多 100。"经过线路"选择器移到 `components/gt/line-filter.tsx`（站点列表、站牌集列表共用），打开弹出层才加载候选（一次 100 条，超出时提示"还有 N 条，输入线路名缩小范围"），输入防抖 200 ms；已选线路的名称用 `ids` 查询。加入线路对话框的搜索也改用它 |

服务端耗时（热缓存，本机）：工作台四个计数接口 224–312 ms → 23–51 ms，四个同时请求 307–359 ms → 61–80 ms；线路列表 100 条 59–80 ms → 34–37 ms。

逐项：

- **压缩（P1）**：首包 JS 1160 KB 原样传输 → 实际传输约 221 KB，CSS 822 KB → 约 148 KB（634 条 `@font-face` 压缩效果很好）；接口 JSON 也压缩，枢纽站详情 166 KB → 36 KB。
- **线路列表不带轨迹（P3）**：线路列表 100 条的接口 1479 KB → 40 KB，服务端 60–80 ms → 35 ms；全局搜索的线路结果随之变轻，一次搜索 159 KB → 8 KB。
- **线路选择器（P4）**：站点列表、站牌集列表打开时不再下载 `/api/lines?size=100`（1.46 MB），接口传输 1.5 MB → 6–12 KB，数据就绪 3.9–4.1 秒 → 0.8–1.4 秒。3000 条线路时已选第 2999 条线路，筛选条正确显示"夜2999路"（手动核对）。
- **编排计数快照（P5）**：数据没变时汇总、队列、"只看待处理"、数据体检都直接读快照，工作台再次访问的数据就绪 546 → 300 ms。写入后的第一次请求要重算，与优化前一样约 300 ms（`sign-sets-perf.test.ts` 在设计规模下：汇总第一次 320 ms、第二次 26 ms；队列 334 → 48 ms；数据体检 557 → 28 ms；"只看待处理 + 按待处理排序" 333 → 46 ms）；数据版本查询本身约 20 ms。
- **按页面分包（P6）**：首包 JS 1160 KB → 695 KB（gzip 后 363 → 225 KB），各页面 4–15 KB（gzip），@dnd-kit 只在站牌集编辑器、线路表单的包里，高德加载器单独成包。首次访问的传输合计里含空闲预取的三组页面：最后一个接口返回之后才开始下载的部分为 91–333 KB（见 10.4 表下），不影响本页的数据就绪。
- **并行请求（P7）**：站点详情与站牌集在同一时刻发出（测量时两者都在约 700 ms 发出、约 760 ms 返回）。实施中发现"站牌集"一节的查询写了 `staleTime: undefined`，盖掉了全局的 15 秒，每次都重新读一遍；改掉后普通站详情的数据就绪从 1711 ms 降到 1103 ms（这次重复读取排在字体后面）。
- **LCP**：各页首次访问约 2 秒 → 0.75–1.2 秒。

没有改善或改善有限的项：

- **字体（Q78，不动）**：现在首次访问的大头是中文字体分片，各页 609–1141 KB（woff2 本身已压缩，不能再压），约占首次传输的六到七成。站牌集列表、线路列表 100 条、站点详情等页的接口在服务端只要几十毫秒，但和约 1 MB 的字体分片共用 10 Mbps 的带宽，数据就绪因此比 LCP 晚 0.3–0.6 秒。字体有长期缓存，第二次访问就没有这部分。
- **再次访问的传输量**：优化前后都只有 1–2 KB。优化前静态资源已经是 7 天 `immutable`，接口响应带 ETag，浏览器再次请求时服务端回 304，所以这一列没有可改善的空间；P2 的效果在超过 7 天之后、或者升级部署之后才显现（只有改了的文件要重新下载）。
- **再次访问的数据就绪**：除工作台（P5）外变化在 0–90 ms 内，枢纽站详情 420 → 434 ms 属于测量波动。再次访问时页面代码都在缓存里，耗时主要是几个接口的往返；304 也要服务端把响应算出来才能比较 ETag。
- **写入后第一次计数请求**：仍是约 300 ms 的重算（计划第 9 节默认决定 4：按数据版本，不按时间过期）。同版本的并发请求只算一次，工作台打开时的四个请求不再各算一遍。
